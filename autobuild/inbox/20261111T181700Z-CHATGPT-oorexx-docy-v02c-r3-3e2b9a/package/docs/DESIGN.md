# DOCY/2 — architecture and implementation boundary

**Architecture concept:** Tom Dyer. **Prototype implementation:** ChatGPT. **Review influence:** Claude (Opus 5.5), November 2026.

## Structural model

A `.docy` snapshot contains one graph composed of independent node, fact, document, template-placement and event records. Each node has a stable, human-meaningful key (`install.prereqs`), a registered type (`section`, `command`, `table`, `svg`, etc.), a recorded author/tool, and typed layered properties. The same node key can occur under many placements across documents, or multiple times in one document. A placement has its own key, document ownership, parent key and order; the placement is not a content copy. In this candidate, parent keys are stored but the renderer currently orders placements flat rather than rendering a nested structural tree.

Templates are documents that own placements and template-level overrides. Their `templateKey` chain is resolved from base to most-derived document, and cycles are rejected by validator STOP. For a property, resolution from highest to lowest priority is: variant override; document override; document/project override; shared project layer; nearest template override; shared template layer; house default. This precedence means a template update does not silently erase a higher-layer value.

## Facts, source truth and dependency closure

`DocyFact` stores key, typed value, source URI, source revision and author. `DocyRef` points directly at its fact key; a node renderer evaluates it only during publication. Tables can hold references per cell. The change-impact planner walks effective placements and node dependencies, deduplicating by document/output path. Because references are typed, it does not need to guess that arbitrary prose happens to mention a source.

**Current limit:** facts in the demonstration are supplied by the fixture. `etc/machines`, actual test-run receipts, package hashes and Storage Fabric have no connected provider adapter in this increment. Automatic polling, file-version pinning and source freshness checks still need implementation. Unknown typed references produce WARN at publish and render a visible unresolved marker, never silent text substitution. The existing StringTemplate package has not been loaded into this candidate. No claim is made that expressions like `{d~Version}` work here.

## Changes

`planNodeChange(...)` and `planFactChange(...)` return a `DocyPlan` with affected output paths, shadow warnings, provenance, and a graph revision fence. A plan leaves authoritative values unchanged. `apply(plan)` rejects a plan when STOP diagnostics exist or the graph revision has changed, and records an ordered logical `DocyEvent`. Shared nodes/facts are updated once. Document outputs are generated by the publisher when called; no automatic fan-out republishing or distributed event bus has been implemented.

In the fixture a single change to `grid.ed209f.address` impacts two Grid Plan outputs and one each in As-built and README. The README's local override remains visible and generates an `OVERRIDE.SHADOWS` warning. The shared `install.prereqs` heading change affects the same documents. The test-run count change reaches only the documents containing the dependent node.

The current event records include sequence, previous event ID, target, layer, author and reason; this is only a **logical predecessor chain**. It is not the cryptographic hash chain used elsewhere in the platform. DOCY/2 snapshots write the full graph. Storage Fabric commit/rollback, durable ordering, signed history, previous/new value provenance, change-set transactions, conflict detection across agents, event replay and delivery acknowledgements must be designed and tested before production use.

## Registered node contract

There are no central store/render `select` branches enumerating node types. `.DocyTypes~install(Model)` registers default classes. Consumers call `Model~registerType('own-type', .OwnNode)` before construction or loading. Custom node classes implement render and record hooks; `test_extension.rex` proves an unknown custom type causes STOP in the default loader, while a registered type round-trips correctly without modification to `DocyStore`.

House-rule validation is expressed via diagnostics: STOP blocks publish, WARN describes an issue, INFO is supported by the bucket structure. Command nodes STOP on trailing period; Credits are mandatory and require architecture, coding and writer; missing author/tool provenance emits WARN; malformed table widths STOP; unsupported node types STOP during load. Loader validation still needs deeper hostile-input hardening, schema version migrators and a broader test corpus.

## Publisher and remaining layers

Markdown and HTML are separate node render methods. TOC derives from effective placements. Tables hold typed cells; SVG source is preserved as a node property, displayed as a percent-encoded passive HTML image, and preserved as a fenced XML block in Markdown (no external asset sidecar yet). XML/SVG sanitization is only a narrow fail-closed guard for common active-content patterns and does **not** constitute a complete SVG sanitizer. Do not publish untrusted SVG as a security-qualified asset.

Remaining architectural priorities:

1. Introduce immutable snapshot/read views and event-only mutations for nodes, placements, templates and overrides; ensure every write is a planned transaction.
2. Integrate native StringTemplate compile/evaluate with scoped resolvers, provenance and typed expression dependencies; no silent unknown expressions.
3. Bind sources through accepted Alchemy source adapters (test runs, machine records, hashes) with revision pins and freshness policies.
4. Implement Storage Fabric event journal and the existing cryptographic hash-chain service, plus multi-agent optimistic transactions and recovery.
5. Add dependency-index invalidation, affected-output queueing, exact format/variant rebuild receipts and incremental publishers.
6. Implement nested placement rendering, cycles across shared references, per-placement overrides, multi-template composition rules, external asset publishing, SVG sanitization and PDF publisher adapters.

**Acceptance scope:** candidate only. Local ooRexx regression and extension tests pass, but integration, concurrent edit, durability and security tests remain outstanding.
