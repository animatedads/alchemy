# ooRexx Logging v0.8 — additive subscription candidate
Architecture: Tom Dyer. Coding and local qualification: ChatGPT.

This is an additive candidate to be overlaid onto the published `oorexx_logging_v0.7` package, **not a complete replacement distribution or a qualified v0.8 release**. Existing LoggingCore is unchanged. Install `src/LoggingSubscriptions.cls` alongside the existing LoggingCore and MethodInterposition dependencies. No kernel, native package, NewShell or daemon dependency. The original upstream v0.7 full suite must still be run by the integration owner; it was not available in this workspace. The supplied NewShell dev6 kit contains the v0.7 core used for these tests (SHA-256 62b3f6b5bd2ad21db01aa83736d440d96035729b8dcccf589982f8196b9537d6).

## Contract
- `LogSubscriptions~new(service, exactScope, budget=4096, handler=.nil)` creates the registry. A default `LogOperationalHandler` retains state notifications; pass a host-owned handler for operational consumption. The configured handler is a trusted authority object, not a proposal capability or cryptographic authentication.
- `register(name,generation,producerClass,methodName,points,priority,capacity)` registers actual `LogRule` and `PriorityLogTarget` objects with the existing service. Maximum 64 subscriptions, aggregate budget max 65536 slots. Rule/target IDs are `LS-<name>`. Freeze registration on first binding; `bind(service,scope,producer)` binds one instance per registered class; multiple different classes supported. Exact case-normalized class/method/point selector. `wants(class,method,point)` checks interest; `publish(producer,method,point,payload,level=.Log~INFO)` uses the actual LogService and matches per-lane delivery. Any payload object is supported. Registered delivery is expected at INFO or higher; no claim of byte-budget or hot-path benchmark. Direct calls outside this registered publication protocol do not receive composite delivery receipts.
- `next(limit)` selects critical, operations, diagnostics in strict order; `target~read(limit)` or `page(generation,after,limit)` returns actual LogEvent objects and cursor; `ack(generation,through)` only acknowledges offered records. CRITICAL rejects new events when full and preserves unacknowledged records; other lanes evict oldest. Cumulative LOST and historical GAP remain visible. QUARANTINED denotes unresolved loss; RECOVERED_LOSS records the count reconciled. No optional mirror can mask a missing/quarantined critical delivery.
- `LOGGING_LOSS`, `LOGGING_LANE_DOWN`, `LOGGING_REARM` go **directly** to configured handler `receive(event)` using structured Directory objects, not through the failed lane or any LogService logging rule. Default handler retains 1024 state events with an explicit dropped count. A host may supply its operational handler at configuration time; callback must not re-enter registry/service or block the publisher. Direct lane disable reports state immediately; service/rule disable is detected by `pollState`, `status`, `next` or relevant publication; host should arrange health checks even when idle. No modification of existing logging core semantics. The independent handler is memory-resident and not an assertion of durable evidence or external notification.
- `rearm(handler,name,expectedLoss,reason)` requires original handler object, operational route, matching current loss count, and available capacity. It records LOGGING_REARM before clearing quarantine; does not erase cumulative loss. Ordinary enabling a rule is not reconciliation. Host must reconcile source/evidence before requesting re-arm. Existing NewShell trigger re-arm authority is not yet wired to this handler. No automatic adaptive pressure control, live subscription reconfiguration, durable Queue Fabric integration, fairness, multi-writer stress or restart recovery. Trusted single-owner publishing/consuming, registered object identity is local not cryptographic.
