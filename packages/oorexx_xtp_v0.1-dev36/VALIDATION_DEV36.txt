3. Review findings (all fixed; docs/SECURITY.md has the table)
  Medium: KEYSOURCE was a label any caller set (1); values were rewritten, so two services
    could look alike (2); a new secret under the same key id went unnoticed and the session
    ran on (3); the test missed regressions in KEYSTATE, PROFILE and the floor (4).
  Low: evidence after close raised (5); acceptor choices and listener floor understated in
    the documentation (6, 7); wrong REASON with neither route nor key (8); a narrow race
    between choosing and reading the key (9); no MODE (10); one state for three cases (11).
  Mutation checks on the fixed code, in a scratch copy, each run against the tests:
    serial check removed         M21 FAIL; ooRexx step 12 FAIL
    KEYSTATE always active       retiring, notyet, expired checks FAIL
    floor raises only from none,
    session PROFILE = protection floor, session-above-profile and acceptor checks FAIL
  Found by the regression: the first serial code was O(n) per key in a reload (P27: 32,000
  keys in 797 ms, worst wait 765 ms). Fixed with the reload's existing hash lookup: 46 ms,
  worst wait 7 ms.

6. Behaviour changes to note
  - Re-installing a key id with a different secret now ends the sessions and message
    contexts under the old secret within about a second, as a revocation does. The same
    secret again changes nothing.

    ldap, file or api.
